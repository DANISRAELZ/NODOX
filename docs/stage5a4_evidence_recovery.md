# Stage 5A.4 — Evidence coverage recovery and audit

Stage 5A.4 follows the completed Stage 5A.2 candidate-discovery benchmark and the Stage 5A.3 ranking-semantics audit. Its purpose is to determine whether missing score-relevant evidence, rather than candidate discovery or model weights, explains benchmark ranking behavior.

Stage 5A.4 does not tune Functional Node Theory or therapeutic ranking weights.

## Why Stage 5A.4 is needed

The H. pylori 26695 Stage 5A.2 run completed Phase 3 over the full 1,554-protein reference proteome and Stage 5A.3 established unambiguous rank/score semantics. However, several evidence layers were unresolved in that run:

- STRING functional-network evidence was unavailable;
- VFDB virulence evidence reported a missing versioned local dataset;
- DEG contextual-essentiality evidence reported a missing versioned local dataset;
- BV-BRC conservation was deferred to the layer resolver;
- DIAMOND host-homology analysis was not enabled.

The three benchmark targets therefore remained hypothesis-only candidates with partial real evidence. Recalibrating weights at that point would risk fitting the model to missing-data artifacts.

## Key recovery principle: freeze candidate discovery

Stage 5A.4 reuses the exact versioned candidate snapshot generated by Stage 5A.2:

```text
<source_run>/stage5a2_candidate_seed_snapshot/
```

It does not query UniProt for a new candidate universe. This preserves the same 1,554 candidates and the same strain/proteome scope. Any downstream score/rank changes can therefore be attributed to evidence recovery and the existing scoring pipeline rather than to candidate-set drift.

## Local DEG/VFDB path recovery

The provider adapters resolve relative `local_dataset_path` values inside each isolated workspace. The base configuration uses:

```text
data_external/deg.csv
data_external/vfdb.csv
```

A dataset stored in the project root can therefore be invisible inside a newly created validation workspace unless it is supplied as an explicit provider path.

Stage 5A.4 resolves datasets using this priority:

1. explicit `--deg-dataset` / `--vfdb-dataset` path;
2. project-root path declared by `config/params.yaml`.

When a project-root dataset exists, Stage 5A.4 passes its absolute path into the isolated recovery run.

The audit also records the dataset SHA-256, size and version-file status. It never silently fabricates or substitutes a dataset.

## Two-step workflow

### 1. Preflight only

Run the audit without contacting providers or recomputing scoring:

```bash
python scripts/run_stage5a4_evidence_recovery.py \
  --source-run-dir results/20260812_hpylori_26695_stage5a2_blind \
  --recovery-run-dir results/20260812_hpylori_26695_stage5a4_recovery
```

This writes:

```text
<recovery_run>/stage5a4_preflight_manifest.json
<recovery_run>/stage5a4_evidence_coverage_before.csv
```

The preflight reports whether DEG and VFDB datasets are present/versioned and whether requested DIAMOND inputs are ready.

### 2. Evidence recovery

After reviewing preflight readiness, rerun score-relevant providers on the frozen candidate snapshot:

```bash
python scripts/run_stage5a4_evidence_recovery.py \
  --source-run-dir results/20260812_hpylori_26695_stage5a2_blind \
  --recovery-run-dir results/20260812_hpylori_26695_stage5a4_recovery \
  --execute-recovery
```

By default this:

- retries STRING;
- enables DEG and VFDB and supplies project-root datasets when found;
- retries BV-BRC;
- keeps InterPro disabled;
- keeps literature metadata disabled;
- keeps DIAMOND disabled unless explicitly requested;
- runs Phase 3 again on the frozen Stage 5A.2 candidate snapshot.

InterPro and literature remain disabled because they are non-scoring in the current benchmark-resilient orchestration.

## DIAMOND

DIAMOND is opt-in so the recovery stage cannot silently change host-similarity behavior.

Execute mode requires an explicit reference FASTA:

```bash
python scripts/run_stage5a4_evidence_recovery.py \
  --source-run-dir results/20260812_hpylori_26695_stage5a2_blind \
  --recovery-run-dir results/20260812_hpylori_26695_stage5a4_recovery \
  --execute-recovery \
  --enable-diamond \
  --diamond-execution-mode execute \
  --diamond-reference-fasta PATH/TO/human_reference.faa \
  --diamond-database-prefix PATH/TO/human_reference
```

Cache-only mode instead requires an explicit cached TSV.

## Recovery outputs

A completed recovery writes:

```text
<recovery_run>/workspace/results/stage5a4_evidence_coverage.csv
<recovery_run>/workspace/results/stage5a4_benchmark_comparison.csv
<recovery_run>/workspace/results/stage5a4_manifest.json
```

The evidence-coverage table separates for each score-relevant layer:

- provider and retrieval status before/after;
- usable evidence before/after;
- whether the layer affected score before/after;
- matched candidate count and coverage fraction;
- evidence level and fallback reason;
- whether usable or score-affecting evidence was newly recovered.

The benchmark comparison reports for PBP1A, GyrA and GyrB (or any benchmarks present in the source trace):

- final rank before/after;
- `meta_priority_score_v3` before/after;
- Functional Node Theory score before/after;
- evidence-quality score before/after;
- Phase 3 confidence/recommendation after recovery.

## Interpretation rules

| Observation | Interpretation |
|---|---|
| provider becomes usable and benchmark rank changes | evidence availability materially affected the existing model output |
| provider becomes usable but rank remains stable | ranking is robust to that recovered layer for the benchmark |
| no score-relevant evidence is recovered | do not infer model failure; fix provider/data availability first |
| evidence improves but benchmark remains implausibly low | downstream model/evidence semantics become a legitimate next target for Stage 5B |
| DIAMOND changes host risk/rank | interpret as selectivity evidence, not as candidate-discovery change |

## Non-goals

Stage 5A.4 does not:

- change Functional Node Theory weights;
- change therapeutic ranking weights;
- change DIAMOND thresholds;
- change candidate discovery or benchmark aliases;
- download or invent DEG/VFDB datasets automatically;
- convert unresolved evidence into negative evidence;
- treat computational evidence as experimental validation.

Only after evidence recovery is quantified should Stage 5B consider any mathematical recalibration.
